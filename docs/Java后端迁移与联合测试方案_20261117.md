## 建议技术方案

采用一个Java应用完成网站，保持当前中文界面和全部核心功能，不引入微服务、Redis或前后端分离工程。

| 层次 | 技术 | 作用 |
| --- | --- | --- |
| 后端入口 | Java 17、Spring Boot稳定版、Spring MVC | 接收网页请求并执行业务；实施时核对依赖仓库并锁定具体版本，不采用SNAPSHOT |
| 页面 | Thymeleaf、现有HTML/CSS/JavaScript | 复用页面外观，将Django模板语法改为Java模板语法 |
| 安全 | Spring Security、BCrypt、Session与CSRF保护 | 登录、密码哈希、权限检查和防止伪造表单请求 |
| 数据访问 | Spring JDBC、连接池 | 使用明确的SQL访问MySQL，便于学习和定位SQL耗时 |
| 数据库迁移 | Flyway版本化SQL | 按顺序建立和升级表，避免依赖自动覆盖表结构 |
| 构建与测试 | Maven Wrapper、JUnit、Spring测试工具 | 固定构建方式，执行功能和权限测试 |
| 并发测试 | Apache JMeter | 10、25、50、75、100用户场景及经单独批准的压力测试 |
| 程序内部分析 | JProfiler | CPU热点、对象分配、堆内存、垃圾回收、线程及JDBC耗时分析 |

整体链路：浏览器或JMeter → Spring Security → MVC控制器 → 业务服务 → JDBC/连接池 → MySQL。JProfiler连接本项目Java进程，记录内部运行情况。

官方要求说明Java 17及Maven 3.6.3以上可用于其当前Spring Boot版本；这仅说明基础版本符合，实际依赖下载、编译和运行仍需验证：[Spring Boot系统要求](https://docs.spring.io/spring-boot/system-requirements.html)。

## JMeter与JProfiler联合测试

JMeter是“模拟来访者”，JProfiler是“观察Java内部工作”。两者分工不同。JProfiler可查看CPU调用树和数据库调用耗时，但不能替代100虚拟用户负载，也不能仅根据内存曲线声称存在内存泄漏。

五类场景仍为首页、列表与详情浏览、不同账号登录、发帖评论、点赞/重复点赞/取消点赞。每类从10、25、50、75到100用户依次执行，不同时开启五组100用户。

| 用户数 | Ramp-up秒 | 所有用户共同运行秒 | 调度设置秒（含3秒边界余量） |
| ---: | ---: | ---: | ---: |
| 10 | 10 | 120 | 133 |
| 25 | 25 | 120 | 148 |
| 50 | 50 | 120 | 173 |
| 75 | 75 | 120 | 198 |
| 100 | 60 | 300 | 363 |

余量用于确保最后一个线程启动后仍有完整稳定时间，最终以线程日志验证共同在线时长。100用户不代表100RPS。实际请求数、成功失败数、平均/P90/P95/P99、吞吐量、错误率、CPU和内存均从原始记录统计。

每档正式成绩先使用不连接JProfiler的基线；需要诊断的场景再以相同负载连接JProfiler记录CPU采样与JDBC数据。内存分配细查、堆快照和可能引起暂停的操作分开进行，并记录采集时间。分析器会增加运行开销，因此报告明确标注采集开关，不能将“开分析器的优化前”与“关分析器的优化后”直接比较。保持Java版本、堆参数、线程池、连接池、数据规模与JMX条件可追溯。

JProfiler JDBC探针可聚合SQL调用和耗时，探针本身也有开销，按需启用：[JProfiler探针说明](https://www.ej-technologies.com/resources/jprofiler/help/doc/main/probes.html)。安装包来自[官方JProfiler下载页](https://www.ej-technologies.com/jprofiler/download)。

停止条件继续包含网站不可用、错误率异常增加、CPU持续接近90%、可用内存持续不足1GB、磁盘不足或严重数据库异常。只停止本项目启动的测试进程，保留中止记录。JProfiler及JMeter均可见操作，启动前核对目标进程，避免连接同机JMeter自己的Java进程。
